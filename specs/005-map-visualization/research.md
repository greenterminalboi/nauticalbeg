# Research: Map Visualization

All findings below are confirmed against the real, trimmed save fixture's
source data (`tools/schema-mapping/inventories/Russia (Melted).md`/`.json`
— generated by `npm run schema-map` against a real save) and the existing
code in `src/parser/version-adapters/1.3.11.ts`, `src/storage/schema.sql`,
`src/storage/queries.ts`, and `specs/003-province-map-generation/`. No
placeholder/guessed field names remain — every raw save field cited here
was observed in the inventory (constitution Principle II).

## 1. Decision: close the location join gap via the save's own `metadata.compatibility.locations` array

**Decision**: `locations.name` is populated at parse time from
`metadata.compatibility.locations[idx - 1]` (1-indexed) — a flat array
of every location's name, in the same order as that save's own
`locations.locations` numeric keys, embedded in the save file itself.
The join against the generated map geometry
(`public/map/provinces.topojson`/`locations.topojson`, decoded
`objects.locations` features' `properties.name`) is name-based, the same
convention `provinces.name` already uses successfully. No change to
`tools/map-generation/` or the committed geometry assets was needed —
the gap closes entirely on the save-parsing side.

This is the result of three attempts, in order; the first two are kept
below for institutional memory, since both were tried, implemented,
tested, and only found wrong at the next stage of scrutiny — an
accurate record of *why* this design won, not just that it did.

### Attempt 1 (disproven): the per-location `name` override field

The original plan was to add a `locations.name TEXT` column, populated
from the raw save's `locations.locations.*.name` field, on the
assumption that it was a general per-location identifier matching the
geometry's own `properties.name`. Tested against a real ~642MB save and
found wrong: `locations.locations[idx].name` is present on only 7 of
28,573 real locations — it's a rare rename-override field (populated
only when a location's name diverges from the game's static default,
e.g. a historical renaming event), not a general identifier. A field
absent for 99.98% of locations cannot serve as a join key.

### Attempt 2 (disproven): `idx` baked into the geometry from `location_templates.txt`'s file order

`map_data/location_templates.txt` (a game-install file, one line per
location, in a fixed declaration order) has exactly 28,573 lines,
matching the real save's total location count exactly, and every name
in it also exists in `named_locations/*.txt` (the file the geometry is
keyed by). The theory: a location's save-side numeric `idx` equals its
1-indexed line position in this file. `tools/map-generation/generate.ts`
was changed to read this file and write a matching `idx` property onto
every decoded location feature (a new `read-location-templates.ts`
module), and both map assets were regenerated against the real local
install.

This looked strong in aggregate — `raw_material` (present in both the
save and the file) cross-checked at ~83%, and the 7 rare `name`-override
samples from Attempt 1 all matched this offset either exactly or via a
clearly-related historical rename (e.g. `ayutthaya` at the position
`ayodhya` occupies by default) — high-cardinality, ~28,000 possible
values, effectively immune to coincidental collision. But it was
**directly falsified** once tested in the running app: sea tiles (e.g.
`gulf_of_danzig`, `gulf_termini`) rendered with real countries' owner
colors, and countries appeared to own land that wasn't theirs (e.g.
`LOT` "owning" Southampton). Checking the save's actual record at the
computed idx for `gulf_of_danzig` (3957) showed a fully-developed real
land town (`development: 30.65`, `rank: "town"`, `raw_material: "wool"`)
— not a sea zone. The file-declaration-order theory was correct for
most of the save but had confirmed, localized misalignments, almost
certainly from the installed game version's `location_templates.txt`
having drifted (entries inserted/reordered by later patches) from
whatever version this particular save was created under — a static
install file has no way to stay correct for an old loaded save. This was
fully reverted: `tools/map-generation/` (including
`read-location-templates.ts`, the `idx` property, and the regenerated
assets) went back to its pre-attempt state, and
`specs/003-province-map-generation`'s docs note the gap was later closed
elsewhere rather than carrying a stale amendment.

### Attempt 3 (adopted): the save's own embedded ordering

The insight: a save doesn't need to reconstruct its location ordering
from an external, version-drifting file — it already embeds one. Every
EU5 save's `metadata.compatibility` block (used for multiplayer
game-data compatibility checking) carries `locations`, a flat array of
every location's name in save-idx order, plus a `locations_hash`
checksum, baked in at save-creation time. Because this array travels
*with* the save, it is immune to the exact version-drift problem that
broke Attempt 2 — old saves carry their own old ordering; there's
nothing external to drift out of sync with.

Validated exhaustively against the real save:
- 0 duplicate names in the 28,573-entry array; every one exists in the
  geometry asset's `properties.name` set (100% structural coverage).
- `raw_material` cross-check: **99.92%** match (vs. ~83% for Attempt
  2) — the residual ~0.08% is consistent with genuine in-game resource
  discovery/depletion, not misalignment.
- The three idx values that were confirmed *wrong* under Attempt 2
  (3957, 3298, 1544) now resolve to real, sensible cities —
  `krosno_odrzanskie`, `verona`, `colmar` — each with a `raw_material`
  that matches its `location_templates.txt` entry exactly. `verona`
  (idx 3298) is owned by `VEN` — Venice historically held Verona,
  explaining the original "VEN owns a gulf" symptom precisely: VEN
  never owned a gulf, it owned Verona, and Attempt 2's misalignment was
  what mislabeled that location as a Baltic sea zone on screen.
- `gulf_of_danzig`'s *true* position under this array (idx 605) has an
  **empty save record** — no owner, no development — exactly the
  signature a sea zone should have. (Sea zones ARE present as entries in
  this array, just correctly ownerless; an earlier hypothesis that they
  should be excluded from the count before computing position was tested
  and made the match rate dramatically *worse*, 6.4%, and was dropped.)
- Confirmed end-to-end through the real parser → schema →
  `listMapLocationsArrow` pipeline (not just at the raw-save level):
  100% of 28,573 real locations resolve a real `name`; `gulf_of_danzig`
  correctly has `owner_idx: null`; `verona` correctly resolves to
  `owner_name: "VEN"`, `raw_material: "wine"`.

**Extraction rule** (`src/parser/version-adapters/1.3.11.ts`):

```ts
const compatibilityLocations = asStringArray(asRecord(metadata.compatibility).locations);
// per location, in the same loop that already reads owner/province/development/raw_material/controller/control:
const name = compatibilityLocations[locationIdx - 1] ?? null;
```

`asStringArray` returns `[]` (not a partial/guessed list) when the block
is missing or malformed — every location's `name` then falls through to
`null`, which this feature's map already renders as neutral "no data"
(spec FR-009), never a fabricated identifier. This matters because the
array's presence across *all* real saves isn't fully confirmed — every
save available for testing was multiplayer-flagged (`compatibility` is
explicitly a multiplayer-sync-checking mechanism); a genuinely
singleplayer-only save that never carries this block is a real,
open possibility, handled safely but not yet observed either way.

**Alternatives considered** (beyond Attempts 1 and 2 above):
- *Bitmap raster-scan order* (locations.png, first-pixel-encountered
  order): tested directly — `idx=1` would be `chukchi_sea` (Arctic),
  contradicting the confirmed `idx=1 = stockholm` from every other
  signal. Disproven outright.
- *Leave the gap open, ship Political/RGO/Control at province
  granularity only*: rejected per the clarify session on 2026-09-19 —
  the user chose to close the gap so all four layers render at true
  per-location detail; Attempt 3 achieves that without the fallback
  ever being needed.
- *A probabilistic/best-effort join, visually labeled as unconfirmed
  per constitution Principle IV*: considered while the join key was
  still uncertain (after Attempt 2's failure), superseded once Attempt
  3 was confirmed at 99.92%+ accuracy with a clear mechanism, not a
  statistical guess.

## 2. Decision: per-location population via `population.pops` → `population.size`

**Decision**: A location's population figure is the sum of `.size`
across every pop record referenced by that location's
`locations.locations.*.population.pops` list (an array of pop-record
IDs), looked up against the existing `population` table's `size` column
(already populated per feature 004).

**Rationale**: Initially assumed (spec.md's Assumptions, written before
this research) that per-population-group records "aren't keyed by
location." That's wrong in one direction — `population.database.*` rows
have no direct location field — but each **location** record carries the
reverse link: `locations.locations.*.population.pops` is a list of the
individual pop-record IDs living in that location (confirmed in the
inventory, e.g. `[117594878, 268590679, ...]`, matching real
`population.idx` values already in the `population` table). This is the
actual raw headcount source; `pop_stats.<type>.population_ratio` (also
present per-location) is a *relative proportion*, not a count, and is
not suitable as "population" on its own.

**Query shape** (joins the existing `population` table by the ids each
location lists):

```sql
SELECT locations.idx,
       COALESCE(SUM(population.size), 0) AS total_population
FROM locations
LEFT JOIN location_pops ON location_pops.location_idx = locations.idx
LEFT JOIN population ON population.idx = location_pops.pop_idx
GROUP BY locations.idx
```

(`location_pops` is a new join table — see data-model.md — since
`population.pops` is a list, not a scalar column, and DuckDB has no
native list-to-rows FK; a real join table is simpler than an unindexed
`LIST` column for repeated per-location sums, consistent with Principle
VII.)

**Alternatives considered**:
- *Derive population from `pop_stats.<type>.population_ratio`*: rejected
  — these are ratios/percentages the game itself computes for its own UI
  display, not raw headcounts; using them as "population" would silently
  misrepresent the underlying data (Principle IV).
- *Store `population.pops` as a DuckDB `LIST` column on `locations` and
  sum via `UNNEST` at query time*: viable but adds an UNNEST join at
  query time for every read; a materialized join table populated once
  during parsing is simpler to index and query, and only one row per
  (location, pop) pair (typically single digits per location) — trivial
  volume either way.

## 3. Decision: country color from `countries.database.*.color`

**Decision**: Add `color_r INTEGER`, `color_g INTEGER`, `color_b
INTEGER` columns to `nations`, populated from
`countries.database.*.color.rgb` (a 3-element array).

**Rationale**: Confirmed present for the large majority of real
countries (`countries.database.*.color`, "sometimes" — some entries,
e.g. rebel/dead/unplayed tag slots, lack it; `FR-009`'s neutral-style
fallback already covers a `NULL` color). `color2`/`color3` also exist
(same shape) but are used for flag rendering, per spec.md's Assumptions
— out of scope unless a future need for distinguishing near-identical
primary colors arises.

**Extraction rule**:

```ts
function asRgbOrNull(value: unknown): [number, number, number] | null {
  const rgb = asRecord(value).rgb;
  if (!Array.isArray(rgb) || rgb.length !== 3) return null;
  const [r, g, b] = rgb;
  return typeof r === "number" && typeof g === "number" && typeof b === "number"
    ? [r, g, b]
    : null;
}
```

## 4. Decision: RGO raw good from `locations.locations.*.raw_material`

**Decision**: Add a `raw_material TEXT` column to `locations`, populated
directly from the existing (but not-yet-extracted) `raw_material` string
field on each location record (e.g. `"clay"`).

**Rationale**: Already sitting on the same location record as
`owner`/`province`/`development` (which `1.3.11.ts` already extracts) —
no new join, no new save section to read, same extraction loop. Absent
for locations with no producible good (open sea, wasteland — confirmed
"sometimes" presence) — the existing `NULL`-safe neutral-style fallback
(FR-009) applies unchanged.

**Color assignment (revised 2026-09-20)**: Originally planned as a
generated categorical palette (evenly spaced golden-angle HSL hues, no
hardcoded goods list) — reconsidered once the user asked specifically
for the game's own RGO colors, not an approximation. The game's own
files do expose real per-good colors, in two steps: every raw good in
`game/in_game/common/goods/*.txt` (5 files: raw_materials,
plantation_goods, produced_goods, food, special) has `category =
raw_material` and a `color = goods_<name>` reference, and every one of
those named colors resolves to an actual `rgb`/`hsv`/`hsv360` value in
`game/main_menu/common/named_colors/02_map.txt`. Resolved this two-step
lookup once against a real local install into a static table
(`src/components/Overview/rgoGameColors.ts`'s `RGO_GAME_COLORS`) and
confirmed it covers all 52 distinct `raw_material` values the real save
(`Russia (Melted).eu5`) actually produces, with 0 gaps. The RGO layer
now uses this table directly; the golden-angle generator is kept only as
a defensive fallback for a raw good absent from the table (e.g. a future
game version adding one this table hasn't been regenerated for) — never
the primary path, so it no longer needs to be "the" design, just a safety
net (constitution Principle IV: represent the real game data, don't
approximate it when the real data is available). The accessibility
requirement (spec Edge Cases, constitution Principle VI) is still
satisfied the same way regardless of color source: every color is paired
with the legend's text label and the tooltip's raw good name, never
color alone.

## 5. Decision: Control layer from `controller` and `control`

**Decision**: Add `controller_idx INTEGER` and `control DOUBLE` columns
to `locations`, populated from the already-present-but-unextracted
`locations.locations.*.controller` and `locations.locations.*.control`
fields.

**Rationale**: Both are direct scalar fields on the same location
record already being read for `owner`/`province`/`development`/
`raw_material` — no additional join. `owner` (already extracted) is the
Political layer's legal-ownership source; `controller` is the Control
layer's current-holder source, confirmed as a distinct field (can differ
from `owner` during occupation, matching the user's original ask).
`control` is a plain `number` (sampled example `1`) — full range not
exhaustively confirmed from a single sample, but consistent with a
0-1 fraction convention used elsewhere in the save
(`market_access`, `cultural_unity`, `religious_unity` in the same
`locations.locations.*` record all sample as 0-1 doubles); the render
layer clamps/normalizes defensively rather than assuming an exact bound.

**Visual encoding** (rendering-layer decision, not a new save field):
color by `controller`'s nation color (same source as the Political
layer), modulated by `control` — e.g. full opacity/saturation at
`control = 1`, fading toward the neutral "no data" style as `control`
approaches its low end — so a solidly-held location reads as solid and
a contested one reads as visibly faded, per spec User Story 5's
acceptance scenarios.

## 6. Decision: additive schema changes via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`

**Decision**: Alongside the `CREATE TABLE IF NOT EXISTS` statements
already in `schema.sql`, add `ALTER TABLE locations ADD COLUMN IF NOT
EXISTS <col> <type>;` / `ALTER TABLE nations ADD COLUMN IF NOT EXISTS
<col> <type>;` statements (DuckDB supports `IF NOT EXISTS` on `ADD
COLUMN`), applied every time a database is opened — not just on first
creation.

**Rationale**: `schema.sql`'s header states "one database per save,"
but saves can be **kept** (`keepSave`/OPFS-persisted, `src/storage/
db.ts`) and reopened in a later session — a kept save's on-disk database
was created with whatever `schema.sql` existed at import time. Without
an additive step, reopening a save kept *before* this feature ships
would hit a hard `column does not exist` SQL error the first time a map
query runs, not a graceful "no data" state. `ADD COLUMN IF NOT EXISTS`
makes reopening safe for both a brand-new database (no-op, column
already exists from `CREATE TABLE`) and an old kept one (column added,
`NULL` for every existing row). Rows with `NULL` new columns then fall
through the same neutral/no-data rendering path the spec already
requires for missing data (FR-009) — no separate re-import prompt needed,
consistent with Principle III's "fail loudly, don't silently corrupt,"
except here there's nothing to fail: a `NULL` value is an honest,
already-specified state, not a misrepresentation.

**Note for implementation**: this is the first feature to add columns to
already-shipped tables via `ALTER`, not just `CREATE TABLE IF NOT
EXISTS`; no prior migration precedent exists in this codebase (confirmed
— feature 004 only added new tables/columns to tables it introduced in
the same feature). Keep the `ALTER` statements colocated with the table
definitions they extend in `schema.sql`, with a comment explaining why
(kept-save compatibility), so a future schema change follows the same
pattern rather than reinventing it.

## 7. Decision: load per-location map data once per save, held in memory (confirmed via clarify)

**Decision**: One query (`listMapLocationsArrow` — see data-model.md/
contracts) returns every location's full per-layer dataset (name, owner,
owner color, controller, controller color, control, raw good, total
population) as a single Arrow IPC buffer when the Map tab is first
opened for a loaded save. The frontend decodes it once via
`apache-arrow`'s `tableFromIPC` (already a direct dependency, used the
same way `src/storage/db.ts` already uses `apache-arrow` internally)
into a plain in-memory structure keyed by location `name` (the topojson
join key from Decision 1). Every layer switch re-colors from this same
in-memory structure; none re-queries.

**Rationale**: Directly resolves the two data-flow clarifications from
the 2026-09-19 clarify session — single stored dataset feeds every
layer, and layer switches don't trigger new queries/loads (spec FR-017,
SC-002). At ~28,573 locations with a handful of small fields each, this
is a low-single-digit-MB in-memory table — well within constitution
Principle V's performance bar, and strictly less total DB work than
re-querying per switch (Option A, rejected during clarify).

**Alternatives considered**:
- *One query per layer, re-run on each switch*: rejected during
  clarification — repeats the same join work on every click for no
  benefit, and risks visible lag on slower client machines.
- *Route through Perspective (this app's existing table-view tool, used
  by `ProvincesTab`/`WarsTab`)*: rejected — Perspective is built for
  tabular grid/chart display with its own virtualization; the map needs
  direct, per-location keyed access for canvas coloring and hit-testing,
  not a grid. Using `apache-arrow` directly (already how `src/storage/
  db.ts` itself decodes Arrow) is simpler and matches the data's actual
  use here (Principle VII).

## 8. Decision: Canvas 2D rendering, hand-rolled linear projection, no new rendering dependency

**Decision**: Render the decoded GeoJSON (via the already-dependency
`topojson-client`) onto an HTML5 `<canvas>`, using a simple linear
(affine) transform from the asset's `[-180,180]`/`[-90,90]` coordinate
space to canvas pixels — not a geographic/spherical projection library.

**Rationale**: `contracts/map-asset-schema.md` (003) already establishes
the asset's coordinates are an equirectangular-projected flat plane, not
real-earth geographic data needing spherical projection math — a linear
scale+pan+zoom transform is both correct and sufficient. No projection
library (`d3-geo`) or heavy map-rendering library (Leaflet, Mapbox GL,
deck.gl) is a current dependency (confirmed: `package.json` has only
`topojson-client` for map-adjacent code), and none of the four layers
need anything those libraries provide beyond fill-coloring flat
polygons. Canvas (vs. SVG) is chosen for the ~28,573-shape scale
(FR-013/SC-006): an SVG DOM with one `<path>` per location plus React
reconciliation on every layer switch risks dropped frames at this
volume; a canvas redraw (fill each decoded polygon, no per-element DOM
node) stays cheap and matches constitution Principle V's "no
unconditional per-data-point rendering cost" guidance in spirit (a
single redraw pass, not one DOM node per location).

**Alternatives considered**:
- *SVG with one `<path>` per location*: rejected — DOM/reconciliation
  cost at ~28k elements risks the responsiveness FR-013/SC-006 require,
  especially on lower-end client hardware (Principle V).
- *A full mapping library (Leaflet/Mapbox GL/deck.gl)*: rejected —
  none of these are current dependencies, all pull in real weight
  (tile-layer/WebGL machinery this project's flat, self-hosted,
  non-tiled asset doesn't need), and Principle VII disfavors adding a
  generic engine for a need this small.

## 9. Decision: hit-testing via a uniform spatial grid + point-in-polygon

**Decision**: For pointer/tap hover-or-select (FR-010), build a
lightweight uniform grid index over each layer's decoded location
polygons' bounding boxes once per save load (alongside the in-memory
data from Decision 7), and resolve a pointer position by checking only
the polygons in the grid cell(s) under the pointer with a standard
point-in-polygon test.

**Rationale**: Canvas has no built-in shape hit-testing (unlike SVG's
per-element event targets), so *something* is needed. A uniform grid is
the simplest structure that avoids checking all ~28,573 polygons on
every pointer move, consistent with Principle VII (no need for a full
R-tree/quadtree library at this scale and this static a dataset — the
geometry never changes after load).

**Alternatives considered**:
- *Off-screen "ID-color" index canvas* (classic technique: render every
  shape once in a unique flat color, read back the pixel under the
  pointer): viable and also considered, but adds a second full canvas
  render pass and pixel-readback round-trip per lookup; the grid+point-
  in-polygon approach is simpler to reason about and test as pure
  functions (no canvas needed to unit-test it).
- *Full spatial-index library (e.g. rbush)*: rejected as an unneeded new
  dependency for a static, single-save-sized dataset (Principle VII).

## 10. Version scope

Only one save-format version adapter exists (`1.3.11.ts`); this feature
extends that adapter only, consistent with every field cited above being
confirmed against that version's real save data. No multi-version
handling is added here (constitution Principle III's version-gating
already exists structurally; this feature doesn't need to extend it).
